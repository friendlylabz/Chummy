# Modules

```
crates/      Pure Rust libraries, each tested on its own
src-tauri/   The app shell: state, IPC commands, native dialogs, windows
ui/          Svelte 5 frontend, one Vite page per window
```

## crates/

| Crate | What it does |
|---|---|
| `flow` | Loops. The `chummy.loop` format (`format.rs`), the **block catalog** (`blocks.rs`: the one source of truth for block types, ports, parameters and help text), validation (`validate.rs`), the **engine** (`engine.rs`: runs a loop against a `Host`), exchanges and tool-call parsing, memory and templates, per-agent overrides (`config.rs`), run log records (`log.rs`), the **loop review** (`review.rs`: what a loop can do, where its data flows, flags) and the built-in loops (`templates/`, generated by `make_templates.py`; `build.rs` hashes them at every build so they're always trusted). |
| `llm` | Model connections: provider configs and presets, adapters for OpenAI-compatible servers, Anthropic and Gemini, streaming (SSE), context lengths, and the **Test connection** probe. |
| `agent` | What an agent is (`Agent`, `AgentTool`, `Permissions`), the configuration it runs under (`AgentConfig`: which model it uses, and how the switches become a run's permissions), and the loop library (`library.rs`: saved loops and built-in upgrades). Shared with chummyd. |
| `session` | Conversations with agents, shared with chummyd: chats (`chats.rs`, with `FileChats` for files), runs (`run.rs`: sending, test runs, pausing and resuming as one response, jobs, answering questions), and paused runs (`paused.rs`). A program implements `Platform` (its configuration, its stores, a run's surroundings, where updates go); `tests/session.rs` runs whole conversations against a test platform. |
| `bundle` | chummyd's bundle: its whole configuration (`Config`, strict, `check()` with errors and warnings), sealed with a password (Argon2id + XChaCha20-Poly1305); password strength and generated passwords. The app's Configure chummyd window writes with it, chummyd opens with it. |
| `channel` | Channels, the same in the app and chummyd. **Kinds** (`kind.rs`): `ChannelKind`, the base every kind of channel implements (what it asks as `Field`s, its checks, the account it logs in as, the texts the windows and `chummyd check` show, who it lets in, and `start`), the registry `kinds()`, and what's generic about them: field checks, `check_bundle`, `derive_key`, address probes (`probe`, judged by the kind's `answers`) and `KindInfo` for the forms. Each kind is a module: `matrix/mod.rs` and `telegram/mod.rs` (always built: the kind itself), with their running side in `matrix/live/` and `telegram/live/` behind the `matrix` and `telegram` features (Matrix: login and cross-signing, rooms, emoji verification, the outbox, uploads; Telegram: the Bot API over HTTPS with no library (`api.rs`, never logging the token), polling, invitation codes, answers as drafts or edits (`outbox.rs`), Markdown as Telegram HTML (`format.rs`), files). A running channel talks to its program through `ChannelHost` and is driven by a `Handle` (`host.rs`): what it asks the user is one generic `Event::Verify`, answered with `Handle::answer`; invitations are `Handle::invite`. How conversations through any channel behave: `conv.rs` (`Conversations` with a program's `Hub` and an `Outlet` per channel; messages, answers, commands, runs shown as they go, questions and approvals, jobs' reports) and `link.rs` (what channels and the conversations tell each other); the commands (`parse`); a run as one message (`RunView`, `figures`, `split`). `files.rs`: saving uploads through the jail. `tests/telegram.rs` runs Telegram against a stand-in Bot API (`tests/support/fake_telegram.rs`, shared with chummyd's tests). **A new kind** is a new module implementing `ChannelKind`, added to `kinds()`: the app's Settings → Channels, Configure chummyd, the bundle, chummyd's state and its commands pick it up from there. |
| `chummyd` | The binary (not built by default): CLI, password input, start-up checks (`checks.rs`), the sealed state folder (`state.rs`), its `Platform` (`platform.rs`), jobs, the router (`router.rs`: the terminal, and the bundle's rules as a `chummy_channel::Hub`) and saving. Its side of the channels (`channels.rs`; the `matrix` and `telegram` features, on by default): starts each channel in the bundle through its kind, with its own folder and key, keeps what each channel keeps in the sealed state, and shows what channels ask in the terminal, answered with `/verify`; `/invite`, `/people` and `/remove` in the router. `tests/terminal.rs` runs it end to end; `tests/matrix.rs` too, against Synapse (`CHUMMY_TEST_SYNAPSE`); `tests/telegram.rs` against a stand-in Bot API. |
| `runner` | Runs an agent: `AgentHost` implements the engine's `Host` with the agent's model, tools, jail, questions and daily budgets. Shared with chummyd. |
| `tools` | Python tools: the PEP 723 header (`meta.rs`), installs and pylock files, the **sandbox backends** (`sandbox/`: Native WebAssembly via Wasmtime, Container, OpenShell), and `NetPolicy`, the only way a tool reaches the web. `builtin/` holds the built-in tools. With the `bundled-python` feature, `bundled.rs` embeds the WebAssembly Python tools run on. |
| `sandbox` | The **folder jail**: validating a workspace choice, the always-refused places (`protected.rs`), and `Jail`, file access through a `cap-std` handle so nothing escapes the folder. |
| `scheduler` | Jobs and triggers, the run planner, folder watching, run history, and the `AskBroker` that carries every question and approval. |
| `log` | The system log, run logs (JSON lines, one file per run), log encryption (XChaCha20-Poly1305, key export with Argon2id), search and retention. |
| `store` | The Chummy folder layout, atomic versioned JSON documents with backups, secrets in the OS keychain, and the **pause vault** (`paused.rs`: paused chat runs sealed with one-time keys held in the keychain). |
| `local` | The basic built-in engine: Hugging Face checks, downloads, memory estimates, the uv-installed runtime, and `engine/chummy_engine.py` (with a `--fake` model for tests). |
| `http` | Shared HTTP clients: the operating system checks certificates, and errors say what went wrong. |

## src-tauri/

- `lib.rs` registers plugins and **every IPC command** (`generate_handler!`);
  `build.rs` lists the command names; `capabilities/*.json` says which
  window may call which command.
- `state.rs` (`AppState`, which holds the `Session` and seals paused runs
  with the pause vault), `settings.rs` (versioned settings and migrations),
  `trust.rs` (the signed list of trusted loops), `platform.rs` (the app as a
  `chummy_session::Platform`: settings, the Chummy folder, the tool sandbox,
  Tauri events), `host.rs` (the app's `Services` for `runner`), `in_app.rs`
  (the only door to model calls outside loops).
- `commands/`: one file per area (chat, agents, providers, loops, tools,
  jobs, logs, sandbox, review…). The chat, job and question commands are
  thin: how runs behave is in `chummy-session`.
- `dialogs.rs`, `windows.rs`, `tray.rs`, `notify.rs`: native dialogs,
  windows, tray and notifications.

## ui/

- Pages: `index.html` (chat), `editor.html` (loop editor), `settings.html`,
  `automation.html`, `chummyd.html` (Configure chummyd), `logs.html`. Each
  mounts `src/windows/<name>/`.
- `src/lib/ipc.ts`: every type mirrored from Rust and every command
  wrapper (with mocks for `npm run dev` in a browser).
- `src/lib/stores/`: shared state (settings, live runs, chat, questions,
  jobs, loops, tools).
- `src/lib/components/`: shared pieces, e.g. `RunTimeline` (a run's log,
  used by the Logs window and **Agent logs** in chat), `ParamFields`
  (block settings), `AskCard` (questions and approvals).
- `src/theme/`: themes are sets of CSS variables; components use only
  those variables.

## How a chat message runs

1. `send_message` (`chummy-session`, called by the app's command) loads the
   agent's loop, checks it, and opens the agent's folder as a `Jail`.
2. `track()` registers the run and starts its log; `run:started` goes to
   every window (through the app's `Platform::emit`).
3. `chummy_flow::run` executes blocks, calling models through `llm` and
   tools through the chosen sandbox backend; each event goes to the log and
   to windows as `run:event`.
4. When it ends, the replies (with the run's figures: time taken, calls,
   steps, tokens) are saved to the chat, and `run:finished` is sent.
5. A paused run (`pause_run`, or a model it couldn't reach) ends the same
   way, with what it said so far, and its `RunState` is sealed for the chat
   (`chummy-session`'s `paused.rs`, kept by the app's pause vault;
   `paused:changed` tells windows). `resume_run` checks the agent, its
   workspace and model, takes the sealed run (deleting it) and carries it on
   as the same run with `run_with` and that state.
